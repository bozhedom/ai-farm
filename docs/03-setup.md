# Запуск и подключения

## Торговый кабинет: основной режим с 12.10.2026

Откройте **http://localhost:3210** и войдите с `OWNER_PASSWORD` из локального `.env`. Главная страница ведёт в торговый кабинет. Инструкция по аккаунту OKX, отдельным Demo/Live ключам, бумажному запуску и допуску к реальным средствам: [21-trading.md](21-trading.md).

Для новой установки: `npm ci`, `npm run setup`, `docker compose --profile app up -d --build`. По умолчанию работает `WORKSPACE_MODE=trading`, реальные заявки выключены. Торговым стратегиям не нужны модель и поиск. Ключи и средства для бумажного режима не нужны. `local:setup` устанавливает модель для студии и для торговли не требуется.

Ниже сохранены общие инструкции инфраструктуры и прежнего текстового продукта. Его витрина теперь находится по `/storefront`, кабинет по `/office/overview`. Для возврата исследовательского расписания требуется `WORKSPACE_MODE=studio`; история и принятые обязательства сохраняются в обоих режимах. При обновлении существующего стенда используйте тот же набор Compose-файлов, что и при его запуске, и сначала проверьте резервную копию.

## Текстовая студия: прежний режим

Приватный репозиторий: [bozhedom/ai-farm](https://github.com/bozhedom/ai-farm). На локальном стенде выбраны бесплатный OpenRouter и SearXNG; ключ уже настроен. Бесплатная альтернатива без облачных ключей — Ollama. Сервис исследует 12 типов услуг, готовит до 12 продуктов, собирает потенциальные открытые запросы заказчиков и выполняет тестовые заказы. Все роли входят в приложение. Сценарии и ограничения новой поставки: [руководство](15-delivery-and-business.md).

**Открыть после запуска: http://localhost:3210.** Для новой установки с Ollama: `npm ci`, затем `npm run local:setup`. Эта команда переключает существующий OpenRouter на Ollama; для уже настроенного OpenRouter используйте [его инструкцию](13-openrouter.md). Текущие изменения проверяются локально; обновление VPS не выполняется.

Ранее стенд был развёрнут на VPS FirstVDS с GPT-6 Astra и SearXNG. Его история описана в [инструкции сервера](10-cloud-vps.md) и [STATUS.md](STATUS.md). Локальная база и база VPS независимы; не заменяйте одну другой. Для локального бесплатного режима настройки платного API не используются.

## Как пользоваться и что проверяем

1. Войдите с паролем `OWNER_PASSWORD` из локального `.env`.
2. Если работа приостановлена, нажмите «Продолжить работу». В «Направлениях» запустите один тип или полный обход. В настройках выберите охват суточного расписания: по очереди или все направления.
3. Система найдёт источники, проверит идею и подготовит контрольный текст. Принятая услуга появится в «Услугах»; при отказе сохранится объяснение. Одно исследование может занять несколько минут.
4. Выберите услугу, подставьте пример, создайте тестовый заказ и подтвердите тестовую оплату. В sandbox деньги не переводятся.
5. Дождитесь отдельной проверки текста. Готовый результат можно прочитать и скачать в TXT. Заказ с ошибкой останется в истории с причиной.

При включённом автозапуске браузер можно закрыть. Компьютер и Docker должны работать. Пауза останавливает новые исследования и заказы, сохраняя выполнение уже принятых заказов. Аварийный стоп запрещает новые вызовы модели.

Доход может появиться от продажи полезного текста покупателю. Эта версия проверяет подготовку услуги и обработку заказа, сохраняет найденные поиском потенциальные запросы в разделе «Клиенты». Она не вступает в переписку, не размещает рекламу и не принимает настоящие деньги. Для реальных продаж отдельно нужны проверка качества, допустимый канал общения и схема оплаты. Ни найденные ссылки, ни одобрение модели не доказывают спрос. Подключение OpenRouter меняет модель, но не открывает публичную продажу.

## Локально: полный стенд в Docker

Нужны Git, Docker с Compose и Node.js 24 для первоначальной генерации `.env`. На компьютере без Node тот же скрипт можно выполнить в временном контейнере Node, сохранив файл с правами владельца.

```bash
git clone https://github.com/bozhedom/ai-farm.git
cd ai-farm
node scripts/setup.mjs
docker compose --profile app up -d --build
docker compose --profile app ps
```

Откройте **http://localhost:3210**. Пароль — поле `OWNER_PASSWORD` в созданном `.env`. Порт выбран отдельно от распространённого 3000, чтобы не занять соседний проект. Если меняете порт, одновременно измените порт Compose и `APP_ORIGIN`.

В Docker запускаются PostgreSQL, приложение, worker, ежедневные копии и observer. Миграции применяются перед приложением автоматически. В новой базе при включённом расписании worker сам создаёт суточное исследование и недельную оценку. При `MODEL_PROVIDER=demo` первые два сервиса появляются на готовых примерах; интернет и модель не вызываются.

Первый проход: войти → «Услуги» → «Попробовать» → «Подставить пример» → создать заказ → подтвердить тестовую оплату → дождаться текста → скачать TXT. Сравнение стратегий и симуляция отбора доступны в настройках. Симуляция изменяет тестовый состав команды; денежный журнал остаётся прежним.

Порт PostgreSQL доступен только с localhost. Кабинет, витрина и результаты закрыты одной сессией владельца. Публичные покупатели и персональные учётные записи в этой версии не включены.

## Локальный ИИ и живой поиск без ключей

```bash
npm ci
npm run local:setup
```

Скрипт останавливает только локальные web / worker, давая активным заданиям до трёх минут на завершение. Очередь и принятые заказы остаются в PostgreSQL. Затем запускает Ollama и SearXNG, скачивает выбранную в `OLLAMA_MODEL` модель (по умолчанию `qwen3:4b`) и включает бесплатные провайдеры. Первое скачивание занимает несколько гигабайт. При ошибке повторите команду; скрытого перехода на демо или облачную модель нет.

После успешной загрузки скрипт устанавливает `APP_ORIGIN=http://localhost:3210`, `SECURE_COOKIE=false`, локальные адреса модели / поиска и разрешает бесплатный автозапуск через `AUTONOMY_ENABLED=true`. Это делает доступным вход даже после настройки `.env` для HTTPS на VPS. Секреты, бюджеты и `PAYMENT_MODE` сохраняются. Файл `.env` записывается атомарно с правами 0600; его прежние копии с ключами не создаются.

Состояние базы скрипт не сбрасывает. Если раньше были включены пауза или запрет расписания, нажмите в панели «Продолжить работу» и «Включить автозапуск». Прежние расходы, версии продуктов и заказы сохраняются. Если активный вызов не успел закончиться перед остановкой, его состояние и резерв требуют обычной проверки; лимиты не обнуляются.

В конце запускаются web, worker, backup и observer. Команда ждёт готовности служб и выводит локальный адрес. Ранее настроенный VPS она не меняет.

Используется `compose.local.yaml` вместе с основным Compose. Ollama ограничен 4 CPU, 6 GB памяти и одним одновременным ответом; SearXNG — 1 CPU и 512 MB. API доступны только на localhost и внутренней Docker-сети. Модель получает JSON Schema, политику и ограниченный контекст. Из потока в панель передаётся количество символов, а полный результат применяется только после валидации. Таймаут одной локальной попытки — 5 минут. При ошибке JSON-схемы допускается одно локальное исправление по замечаниям валидатора; причины и повтор записываются в журнал. Неисправленный ответ не публикуется.

Плата за модельные / поисковые API в этом варианте равна нулю; процессор, RAM, диск и электричество всё равно расходуются. Маленькая модель может ошибаться, а общедоступные поисковики — возвращать таймауты или ограничения. CAPTCHA не обходятся. Если независимых источников меньше двух, исследование останавливается. SearXNG передаёт поисковые фрагменты, не полное содержимое страниц. Для устойчивой эксплуатации можно отдельно переключить модель или поиск на Yandex.

В `compose.local.yaml` установлен `LLAMA_ARG_CACHE_RAM=0`: отключён дополнительный кеш прошлых промптов внутри llama-server. Его исходный предел 8 GiB превышал лимит контейнера 6 GB и приводил к OOM при смене ролей. Параметр подтверждён встроенным `llama-server --help` закреплённого образа и [документацией llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). Модель, её контекст, история в PostgreSQL и том с весами сохраняются; повторная обработка промптов может занимать больше времени. После обновления Compose примените настройку командой `docker compose -f compose.yaml -f compose.local.yaml up -d --no-deps ollama`, предварительно дождавшись завершения текущих модельных задач.

Последующие команды для этого варианта:

```bash
docker compose -f compose.yaml -f compose.local.yaml --profile app ps
docker compose -f compose.yaml -f compose.local.yaml --profile app up -d --build web worker backup observer
```

Перед взятием задания worker проверяет локальные службы: наличие выбранной модели через `/api/tags`, доступность поиска через `/healthz`. Это работает и после перезагрузки Docker, когда порядок `depends_on` сам по себе не гарантирован. Пока поиск недоступен, исследования остаются в очереди без расхода попыток; готовая модель может выполнять уже оплаченные заказы. Переходы доступности записываются в журнал. Healthcheck подтверждает доступность службы, а не достаточность источников или качество модели.

Для VPS с доменом добавьте `-f compose.edge.yaml`; не публикуйте порты Ollama, SearXNG или PostgreSQL наружу. Порядок показа работы — [сценарий демонстрации](04-live-demo.md).

Основания интеграции: [Ollama Docker](https://docs.ollama.com/docker), [структурированные ответы](https://docs.ollama.com/capabilities/structured-outputs), [Qwen3 4B](https://ollama.com/library/qwen3:4b), [SearXNG Search API](https://docs.searxng.org/dev/search_api.html). Ресурсы выше — выбранные ограничения нашего стенда, не обещание скорости провайдера.

## Разработка без пересборки контейнеров

Не запускайте второй web на том же порту. Worker можно запускать отдельно; для разработки достаточно одного экземпляра.

```bash
npm ci
npm run setup
docker compose up -d db
npm run db:migrate
npm run dev
```

Во втором терминале:

```bash
npm run worker
```

Nuxt dev читает `.env`; команды worker и миграций используют `--env-file=.env`. Production Node сам `.env` не читает; Compose передаёт его через `env_file`.

## Подключение OpenRouter после локальной проверки

Адаптер поддерживает бесплатные модели OpenRouter. Живой цикл проверен 06–07.10.2026; модель может быть временно недоступна или нарушать формат ответа. Нужен личный API-ключ, записанный только в локальную `.env`.

```dotenv
MODEL_PROVIDER=openrouter
OPENROUTER_API_KEY=your-key
OPENROUTER_MODEL=dots-studio/dots-3-note-preview:free
OPENROUTER_REASONING_EFFORT=low
SEARCH_PROVIDER=searxng
```

Сервер допускает `openrouter/free` и модели с суффиксом `:free`, но поддержка имени не гарантирует доступность маршрута. В проверке 06.10 `openrouter/free` возвращал 404 при запрете сбора данных; использовалась модель из примера выше. Платные запасные модели запрещены. После настройки пересоздайте web / worker, сохранив локальные поиск, БД и историю:

```bash
docker compose -f compose.yaml -f compose.local.yaml --profile app up -d --force-recreate web worker
```

Сначала проверьте исследование и заказ вручную, затем при подходящем качестве включите автозапуск. У бесплатного API возможны ограничения и ошибки; система сохраняет их вместо выдуманного результата. Подробности и проверка подключения: [OpenRouter](13-openrouter.md).

## Облачная альтернатива: Yandex

Yandex — уже реализованный адаптер, а не обещание максимального качества. Для выбора более сильной модели и первого платного теста прочитайте [отдельный гайд](07-paid-ai.md); OpenAI / GPT-6 Astra уже подключён и проверен; Claude пока требует адаптера.

1. Откройте [консоль Yandex Cloud](https://console.yandex.cloud/), создайте облако / каталог и платёжный аккаунт. Сохраните ID каталога.
2. Создайте отдельный сервисный аккаунт проекта. Назначьте на каталог `ai.languageModels.user` для Text Generation API и `search-api.webSearch.user` для поиска. Подтверждённые инструкции: [аутентификация модели](https://aistudio.yandex.ru/ru/docs/ai-studio/api-ref/authentication), [аутентификация поиска](https://aistudio.yandex.ru/ru/docs/search-api/api-ref/authentication).
3. Создайте API-ключ с доступом к этим API. Если консоль предлагает scopes, выберите выполнение запросов к текстовым моделям и Search API по [актуальному списку](https://yandex.cloud/ru/docs/iam/concepts/authorization/api-key). Не выдавайте роли владельца облака.
4. В `.env` задайте:

```dotenv
MODEL_PROVIDER=yandex
SEARCH_PROVIDER=yandex
YANDEX_FOLDER_ID=your-folder-id
YANDEX_API_KEY=your-api-key
YANDEX_MODEL=yandexgpt/latest
```

Используется нативный Text Generation API Yandex, а не подписка на чат. Конкретный URI модели должен быть доступен в вашем каталоге. `latest` удобно для первого теста; после проверки качества зафиксируйте доступную версию модели. Недоступный URI / отказ API останавливает задачу, без скрытого перехода на демо.

5. Сверьте `MODEL_INPUT_KOPECKS_PER_1K`, `MODEL_OUTPUT_KOPECKS_PER_1K`, `SEARCH_COST_KOPECKS` с [тарифом модели](https://aistudio.yandex.ru/ru/docs/ai-studio/pricing) и [тарифом поиска](https://aistudio.yandex.ru/ru/docs/search-api/pricing). По умолчанию стоят консервативные расчётные значения 100 / 100 копеек за 1 000 токенов и 60 копеек за поиск, **не обещание действующего тарифа**.
6. Перед переключением завершите тестовые заказы, сохраните backup и пересоздайте web / worker:

```bash
docker compose --profile app up -d --force-recreate web worker
```

После переключения можно запустить новое исследование кнопкой: суточной квоты и задержки между завершёнными ручными заданиями нет. Пока исследование в очереди или выполняется, повторное нажатие возвращает то же задание. Денежные лимиты продолжают действовать, история и расходы сохраняются. Для изолированной приёмки live-интеграции используйте отдельный стенд / БД.

Учёт расходов рассчитывается из usage API и настроенного тарифа. Неоднозначные вызовы учитываются по зарезервированному максимуму. Это операционный учёт, не банковская выписка. Неверный тариф в конфигурации, смена тарифов или расходы вне приложения требуют сверки с кабинетом провайдера. Дополнительно настройте доступные квоты и уведомления о бюджете на стороне Yandex.

## Криптовалютный тест

По умолчанию `PAYMENT_MODE=sandbox`: кнопка доступна только авторизованному владельцу, перевод не выполняется. Утилита `npm run wallet:test` создаёт отдельный тестовый адрес, записывает ключ в `.secrets/sepolia-test-wallet.json` (0600), заполняет пустые `SEPOLIA_RECEIVER` / `SEPOLIA_RPC_URL` и проверяет сеть / баланс. Повторный запуск сохраняет тот же адрес. Утилита не меняет `PAYMENT_MODE` и не подписывает переводы. Приложение получает **только публичный адрес**; `.secrets` исключён из Git, Docker и форматирования. Сохраните этот файл отдельно, используйте адрес только для тестового ETH.

По [документации Ethereum](https://ethereum.org/developers/docs/networks/) выберите действующий faucet для Sepolia и RPC-провайдера. Доступность бесплатных лимитов меняется; требования регистрации / верификации выполняет владелец. Тестовый ETH не покупайте. В приложении не требуется баланс mainnet.

```dotenv
PAYMENT_MODE=sepolia
SEPOLIA_RPC_URL=https://your-sepolia-provider.example/your-endpoint
SEPOLIA_RECEIVER=0xYour40HexCharacterAddress
SEPOLIA_CONFIRMATIONS=3
```

Перезапустите web и worker, создайте **новый** заказ. Скопируйте точную сумму с 18 десятичными знаками и адрес, отправьте native ETH в Sepolia, укажите transaction hash. Кошелёк может округлять отображение, поэтому перед подтверждением проверьте все знаки. Сумма содержит уникальную часть счёта. Перевод ERC-20, mainnet, неверная сумма, другой получатель, неуспешный или старый перевод не принимаются.

Система проверяет chain ID 11155111, hash, статус receipt, native transfer без вызова контракта, сумму wei, получателя, соответствие canonical block, время и минимум 3 подтверждения. Одна транзакция не может закрыть два заказа. До подтверждения выдача не начинается. Это доверие выбранному RPC и порог подтверждений; абсолютная финальность и защита от злонамеренного RPC не обещаются. Для реальных средств потребовался бы другой уровень сверки.

Автоматического вывода, подписи транзакций и возвратов нет. Ошибка тестового заказа отображается как `manual_review`. Ни тестовый ETH, ни sandbox не включаются в выручку. Реальная криптооплата не включается настройкой окружения.

## VPS и HTTPS

На текущей машине подготовлена отдельная пара SSH-ключей: публичная часть `.secrets/vps_deploy.pub`, приватная `.secrets/vps_deploy` (0600). При создании VPS добавьте содержимое `.pub` в поле SSH key хостера. После этого нужны IP и имя SSH-пользователя; домен можно подключить позже. Приватную часть не передавайте. На другой машине создайте свою пару `ssh-keygen -t ed25519`.

После выдачи SSH-доступа можно выполнить ту же установку на VPS. Репозиторий приватный: используйте GitHub CLI под разрешённым аккаунтом или read-only deploy key. Не копируйте личный GitHub token в Dockerfile.

Домен должен указывать на VPS; порты 80/443 — доступны извне. В `.env`:

```dotenv
DOMAIN=farm.your-domain.example
APP_ORIGIN=https://farm.your-domain.example
SECURE_COOKIE=true
```

```bash
docker compose -f compose.yaml -f compose.edge.yaml --profile app up -d --build
```

Caddy получает сертификат и проксирует приложение. БД и порт 3210 оставьте только на localhost. SSH ограничьте вашим доступом. Не включайте HTTP для удалённого кабинета. Текущий VPS использует отдельный Caddy с сохранёнными сертификатами; точная конфигурация описана в docs/10-cloud-vps.md.

## Эксплуатация и восстановление

- `docker compose --profile app ps` — состояние и healthcheck служб.
- `docker compose logs --tail=100 worker` — сбой инфраструктуры; детали заданий видны в панели.
- «Пауза» запрещает новые исследования / заказы, продолжает принятые обязательства. «Остановить» запрещает новые модельные вызовы. Уже отправленный API-запрос может завершиться и быть учтён; сверка платежей не останавливается.
- Расписание использует UTC, а интерфейс показывает часовой пояс браузера. Еженедельные слоты привязаны к UTC-эпохе; первый отчёт появляется при запуске. Минимальная зрелость денежной оценки — отдельное правило 14 дней.
- `AUTONOMY_ENABLED=false` запрещает автоматические исследования, включая уже стоящие в очереди. Недельная оценка бесплатна и выполняется независимо от этого флага, модели и поиска. При `true` расписание можно выключать в панели; переключатель хранится в БД. Начатая работа может завершиться. Панель показывает последний автоматический запуск и причину ожидания; heartbeat не доказывает качество модели.
- После 28 суток без подтверждённых продаж сервер закрывает окно при ближайшем цикле worker или попытке исследовательской работы, не ожидая следующего недельного отчёта. Предельный срок проверяется по часам PostgreSQL перед запуском, новым модельным вызовом и публикацией. Ожидающие исследования завершаются с сохранением истории/расходов и закрытием резервов; поздний результат начатой работы остаётся в истории без выпуска продукта. Принятые заказы продолжают исполняться. Владелец может открыть новое окно в панели после пересмотра гипотезы; каждое закрытие сохраняется отдельно, даже без смены поколения.
- При неопределённом исходе API-вызова автоматическое повторное списание запрещено. Запись `uncertain` требует сверки. Удалять её для обхода лимита нельзя.
- В этом пилоте уведомления — журнал и панель, плюс Docker healthcheck. Отдельный `observer` раз в минуту сохраняет проверки `/api/readiness` в `.health/`: доступность БД, свежесть worker, сверки платежей, копии и предварительной проверки модели/поиска. Отказ зависимости или проверка старше 90 секунд дают HTTP 503 даже при живом worker. `/api/health` проверяет только web/БД и используется для запуска контейнеров. Генерация и облачные API контрольным запросом не проверяются; это явно подписано в панели. Новая история v2 отсчитывает свои 48 часов; прежняя история сохранена отдельно как наблюдение инфраструктуры. Сбой и пропуск сбрасывают непрерывный интервал. Почта / Telegram / внешние аварийные оповещения ещё не подключены.
- При обычном `docker compose restart worker` текущий внешний вызов завершается и сохраняется, следующий новый учётный вызов не начинается. Единственная встроенная бесплатная коррекция JSON-формата относится к текущему вызову и может завершиться после сигнала остановки или срока окна. Безопасно остановленное задание возвращается в очередь с теми же ответами, расходами, планом и резервом, без расхода попытки. Смена суток не удаляет такой остановленный шаг. В Compose предусмотрено до 21 минуты на один максимальный вызов Ollama и единственную коррекцию формата; обычно остановка значительно быстрее. `SIGKILL`, отключение питания и превышение этого времени не являются штатной остановкой.
- После аварийного завершения аренда задания истекает через две минуты. Сохранённые успешные ответы используются повторно. Если результат отправленного вызова неизвестен, он не отправляется заново: заказ получает ручной разбор, расходы и доказательства остаются. Заказ старше 30 минут с момента тестовой оплаты также требует разбора; длительный простой нельзя обещать восстановить полностью автоматически.

Подробный порядок и критерии наблюдения — [дни 16–20](12-days11-20.md). Перед первым запуском новых служб выполните `npm run setup`: кроме `backups/` он создаёт `.health/` для несекретных статусов. Web получает только чтение этого каталога; observer и backup — запись.

Контейнер `backup` делает снимок при старте и затем каждые 24 часа, хранит примерно семь суток. Файлы в `backups/` содержат данные и сессии; защищайте их так же, как БД. Копия на том же VPS защищает от ошибки приложения, но не от потери диска. До реального рынка нужна копия в отдельном защищённом хранилище в подходящем регионе.

Ручная копия и проверка восстановления в **новую временную БД**:

```bash
sh scripts/backup.sh
sh scripts/restore-check.sh backups/farm-TIMESTAMP.dump
```

Вторая команда не заменяет рабочую БД; временная БД удаляется после проверки. Для аварийного восстановления: остановить web / worker, сохранить текущую повреждённую БД отдельно, восстановить проверенный dump в новую БД, сменить DATABASE_URL, аннулировать сессии и проверить состояния очереди перед стартом. Исход внешнего вызова после потери данных может быть неизвестен — это требует сверки, не слепого повтора.

## Проверки разработчика

```bash
docker compose exec -T db createdb -U farm farm_test
npm run typecheck
npm test
npm run test:integration
npm run build
npm run format:check
```

Если `farm_test` уже есть, повторно создавать её не нужно. Интеграционные тесты очищают только БД с суффиксом `_test`, заданную `TEST_DATABASE_URL`; рабочую БД не используйте. GitHub Actions выполняет те же проверки в отдельном PostgreSQL.

Для отдельной проверки настоящих процессов, расписания и перезапуска создайте **новую пустую локальную** базу, например `farm_autonomy_run_test`, и задайте её URL в `AUTONOMY_DATABASE_URL` локального `.env`. Адрес должен вести на `localhost`, `127.0.0.1` или `::1`, без query-параметров. Пароль берётся из вашей установки и не передаётся в переписку.

```bash
docker compose exec -T db createdb -U farm farm_autonomy_run_test
npm run test:autonomy
```

Проверка отказывается работать с непустой базой; для повторного запуска выберите новую. Она сама применяет миграции, запускает два worker, проверяет полный обход, исполнение заказов при паузе, SIGTERM, недоступность модели и SIGKILL с настоящим ожиданием двухминутной аренды. После запуска сохраняет базу и отчёт `output/autonomy/*.json`, завершает только свои дочерние процессы. Обычно требуется несколько минут. Ответы модели и оплаты здесь синтетические; реальные адаптер HTTP, очередь и процессы проверяются без облачных вызовов и списаний. Это не оценка качества настоящей модели и не подтверждение настоящих продаж.

Внешняя приёмка после подключения: один реальный поисковый запрос и модельный цикл с измеренным usage; один настоящий Sepolia testnet-перевод; перезапуск с незавершённым заданием; восстановление backup; 48 часов наблюдения на целевом VPS. Эти проверки нельзя заменить mocked-тестами.

### Публикации с локальной моделью

При проверке Qwen3 4B обнаружено искажение исходных фактов, которое та же модель ошибочно одобряла. Поэтому локальный рецепт публикаций ограничен тремя вариантами оформления **полного исходного текста**, без сокращения и перефразирования. Модель выбирает оформление; сервер сохраняет каждую фразу и исходный порядок во всех трёх вариантах. Отдельная модельная проверка остаётся. Это форматирование, а не три новых рекламных текста.

Материал ограничен 3 000 символами; полный размер результата проверяется до создания заказа. Новые версии сохраняют точное обещание услуги. Прежние версии публикаций нужно обновить исследованием перед заказом через Ollama; уже принятые заказы со старым обещанием не переписываются и требуют проверки. Заказ с новым рецептом сохраняет его и после переключения провайдера. Описания и FAQ по-прежнему генерируются моделью и требуют проверки на ваших материалах.
