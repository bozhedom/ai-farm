# Цикл фермы: идеи, продукты, клиенты, отчёт

Ферма работает сама по суткам UTC. Руководитель здесь это серверный код, а не модель: он раздаёт задачи, считает баллы и следит за бюджетом. Модели только отвечают по схемам; действия выполняет сервер.

## Как проходит день

1. **Задания.** Каждому из четырёх разведчиков сервер даёт тему из таксономии (`core/taxonomy.ts`: 18 отраслей, 36 тем). Сначала темы из отраслей агента, давно не разведанные; у разных агентов в один день разные темы и отрасли. В ленте: «Руководитель раздал задания: Разведчик А ищет на маркетплейсах, Б в общепите…».
2. **Разведка** (`scout`). Два поиска по серверным фразам темы (спрос и конкуренты), до 12 источников. Разведчик возвращает идею: аудитория, проблема, признаки спроса со ссылками только из выдачи, конкуренты, модель дохода, расходы, риски, быстрый тест и честная оценка «ферма сделает сама». Критик спорит. Повтор старой идеи (тот же отпечаток или сходство от 0,6) получает «на доработку».
3. **Отчёт** (`report:daily:<день>`), когда все разведки дня закончились. Сервер ставит статусы. Принята критиком и исполнима фермой: «принята». Принята, но нужна работа людей: «нужен человек» с планом запуска. Отклонена критиком: «отклонена». Балл 0..100 считает сервер. Модель «Руководитель» пишет короткий текст по серверным цифрам; если модель недоступна, отчёт сохраняется с цифрами. Модель видит цифры и статусы русскими словами, без кодов. Текст проверяется (`reportIssues` в `core/policy.ts`): без латиницы в русском тексте, кодов вроде HOLD и REVISE, идентификаторов идей и советов менять или подтверждать цену, бюджет или лимиты; длинное тире сервер заменяет дефисом. Бесплатная модель исправляет ответ один раз, иначе отчёт остаётся с цифрами.
4. **Сборка продукта.** Отчёт отправляет лучшие принятые идеи на исследование (`idea-research:<id>`, не больше `IDEA_PRODUCTS_PER_DAY` в день, по одной на тип услуги). Прежний конвейер проверяет шаблон и контрольный пример; при успехе продукт выходит на витрину: цена из серверного списка, страница, ссылка на идею. Обещание по умолчанию и «Что получите» берутся из серверного каталога; от модели только заголовок под нишу, «кому подходит» и ограничения. Их проверяет `productOfferIssues`: русский текст без чужой латиницы, иероглифов, служебных слов, двух точек и обрывов, а заголовок называет эту услугу (слова типа услуги из `templateTopicWords`). Пример на странице это ответ модели на серверный контрольный материал шаблона; он проверяется так же. Идея строится только в свой тип услуги, демо-идея на стенде с настоящей моделью не строится. Бесплатная модель исправляет страницу один раз. Если сборка не прошла, продукт не выходит, идея получает статус «нужен человек» и причину в `ideas.build_error` («Сборка не прошла проверку: …», миграция 025), событие `idea_build_failed`.
5. **Клиенты** (`lead:<день>:<продукт>`). Для продуктов на витрине сервер ищет публичные запросы и готовит отклики (не больше `LEAD_DRAFTS_PER_DAY` в день). Отклик проверяется: без почты, телефонов, @-упоминаний, чужих ссылок, скидок и гарантий; единственная ссылка ведёт на страницу продукта; русский текст без иероглифов и латиницы (кроме брендов и слов из самого запроса). Отправляет только человек. Закрытые запросы («Закрыт», «исполнитель выбран»), работа для студентов («для дипломной») и запросы, где самая новая дата в заголовке или фрагменте старше 60 дней, отбрасываются (`staleLead`); такие уже сохранённые запросы получают `reply_error` `LEAD_CLOSED`, `LEAD_EXCLUDED` или `LEAD_TOO_OLD` и не тратят дневной лимит. На стенде с настоящей моделью отклики готовятся только для не демо-продуктов на витрине.
6. **Отбор агентов** (`evolve`), когда у всех хватает идей. Подробно в [20-evolution.md](20-evolution.md).

Еженедельно, как и раньше, проходит денежная проверка (HOLD без продаж) и недельный отчёт руководителя.

## Очередь и ограничения

- Приоритет: заказы, отбор, отчёт, исследование, разведка, клиенты. Задания модели фермы идут по одному, даже при двух worker.
- Пауза, остановка и закрытый сезон останавливают новую работу фермы. Отбор идёт и на паузе (с решением «ждём»), но не после остановки.
- Задания по расписанию ждут, если расписание выключено. Кнопка «Найти идеи сейчас» (`POST /api/office/scout`) работает и без расписания: после последней ручной разведки сам ставится отчёт, идеи получают статусы, лучшие идут в сборку.
- Не больше 24 идей в день (`POLICY.maxIdeasPerDay`), сколько бы раз ни нажимали кнопку.
- Продукт, который владелец скрыл, остаётся скрытым: сборка по новой идее выпускает версию, но на витрину её не возвращает. Отклики готовятся только для продуктов на витрине.
- Платные провайдеры откладывают деньги под задачу (`SCOUT_RESERVE_KOPECKS`, `LEAD_RESERVE_KOPECKS`, `REPORT_RESERVE_KOPECKS`). Если кончился только дневной лимит, задача ждёт завтра. Бесплатные модели ничего не откладывают.
- Вчерашние неначатые разведки и поиски клиентов пропускаются, очередь не копится. Это касается и ручных разведок по кнопке «Найти идеи сейчас» (как и ручных исследований): их день это день нажатия, кнопку можно нажать снова. Если в ручной пачке часть разведок успела пройти, отчёт по их идеям всё равно ставится.
- Вызов бесплатной модели (OpenRouter `:free`, Ollama), прерванный ошибкой или перезагрузкой, повторяется: событие `tool_call_retried`, прежняя запись остаётся под ключом с `:retired:`. Зависший вызов без сигнала две минуты считается брошенным; пока он моложе, задание ждёт (`FREE_CALL_STILL_RUNNING`). Для платных провайдеров, а также при ошибках про плату или политику, остаётся `UNCERTAIN_CALL_REQUIRES_REVIEW`.

## Настройки владельца

`POST /api/office/settings`: разведок на агента в день (по умолчанию 1), поисков клиентов в день (4), отбор вкл/выкл, порог идей для отбора (6), отборов в день (1). Денежные лимиты меняются только в окружении сервера.

## Подготовка показа

`npm run demo:prepare -- --cycles 3 --min-ideas 2` прогоняет несколько циклов: разведка всеми агентами, отчёт, сборка продуктов, поиск клиентов, отбор с порогом 2 (после него порог возвращается). Работает только на базе, имя которой (по `current_database()`) оканчивается на `_test`, или с явным флагом `--i-know-this-is-production`. Демо-провайдер эту проверку не снимает. Демо-продукты попадают на витрину только на стенде с `MODEL_PROVIDER=demo`; на стенде с настоящей моделью витрина их не показывает, а кабинет не даёт их опубликовать. Там же демо-идеи не идут в сборку, демо-продукты не получают откликов, а цифры и рейтинг отчёта, «В продаже» на главной считают только настоящие данные (`core/stand.ts`). Демо-данные помечены `is_demo` и ссылаются только на example-домены. Чтобы на витрине было больше продуктов, временно поднимите `IDEA_PRODUCTS_PER_DAY` (до 12).

## Живая проверка (08.10, бесплатный OpenRouter и SearXNG)

База `farm_b_test`, модель `dots-studio/dots-3-note-preview:free`, поиск SearXNG на 127.0.0.1:8088, тема «Карточки товаров на Ozon и Wildberries».

- Разведка: 109 с. Поиск 12 источников с 11 доменов (13 с), идея 56 с, критик 39 с, 0 ₽. Обе роли один раз исправляли формат: разведчик сослался на URL не из выдачи, критик превысил 700 знаков. После исправления ответы прошли проверку.
- Идея «Сервис оптимизации карточек товаров для маркетплейсов на ИИ»: честно «нужен человек», шесть признаков спроса со ссылками на найденные сайты, конкуренты с ценами, план запуска. Критик дал «на доработку»: идея повторяет существующие сервисы и требует интеграций. Балл 63.
- Отчёт: 16 с, текст прошёл проверку. Слабое место: модель сослалась на идею по её id и предложила владельцу шаг для идеи «нужен человек», хотя статус был «на доработку».
- Первый прогон без продления аренды упал с `LEASE_LOST`: разведка длиннее двух минут аренды. Worker продлевает аренду сам; `demo:prepare` исправлен и тоже продлевает.

Сделать вывод о качестве идей по одной разведке нельзя. Спрос в выдаче поиска не доказывает продаж.
