# Project instructions

Отвечай по-русски, кратко и по делу. Обычные обратимые действия выполняй самостоятельно.

## Architecture

- Nuxt 4 / Vue / TypeScript, PostgreSQL, separate Node worker, Docker Compose.
- Read `docs/01-project-plan.md`, `docs/03-setup.md` and `docs/STATUS.md` before continuing significant work.
- Models produce validated data. Only server code performs actions. Never grant models shell, SQL, secrets, policy editing, wallets or unrestricted network access.
- `prompts/master.md` is shared by every model role. Hard limits belong in `core/policy.ts` and database transactions, not only in prompts.
- Sandbox and Sepolia are test modes. Never count test payments as revenue. Mainnet and real cryptocurrency sales are intentionally unavailable.
- The owner authorized a separate multi-exchange spot-trading product (OKX, Bybit, Binance, Bitget) on 12.10.2026. Ledgers, agents, orders and risk history are isolated by exchange and paper/demo/live mode. The owner clarified that 100 USDT was an example, not a funding ceiling: initial live allocations are owner-defined, remain immutable after activation and must pass exact-input, minimum-capital and exchange-balance checks. The owner also authorized local-only dynamic discovery and rotation of eligible USDT spot pairs through a bounded, deterministic market scout; fixed BTC/ETH allowlists are no longer the trading scope. Only server code can submit cash IOC orders admitted by the current scout and execution checks; models never get keys or trading tools. Live trading needs local credentials, explicit enablement and the enforced acceptance gates. Transfers, withdrawals, margin and derivatives remain unavailable. See `docs/21-trading.md`.
- Money uses integer kopecks; on-chain values use integer wei strings / BigInt. No floating point accounting.
- The owner authorized local development of additional earning directions on 13.10.2026. Grid/DCA are paper-only. Public funding, prediction, DeFi and cross-exchange observations have no execution authority. The service API reuses test orders and owner authentication; it is not x402 or a production payment rail. See `docs/25-earning-workspace.md` for readiness and customer prerequisites.
- The owner authorized a local LLM trading manager on 13.10.2026. It proposes bounded Paper experiments through validated data and a durable task queue; server code applies and evaluates them. It cannot start trading, clear stops, edit policy/capital, operate Demo/Live or execute arbitrary tasks. Manager costs share the existing ledger and global budgets with additional limits in `MANAGER_POLICY`. See `docs/26-trading-manager.md`.
- On 13.10.2026 the owner explicitly authorized publishing the market scout, earning workspace, manager and handover documents to the existing VPS. This supersedes the earlier local-only deployment restriction for these features. Preserve server credentials, trading allocations, risk history, existing stops and paid-model limits; publishing does not authorize Live or clearing the existing model-work emergency stop. See `docs/34-launch-timeweb.md`.
- Later on 13.10.2026 the owner explicitly authorized developing execution for arbitrage, funding, DeFi and prediction markets, **local only; do not deploy**. This is a separate `core/execution` product: prefunded spot arbitrage, isolated 1x Bybit spot/perpetual hedges, bounded Aave USDC supply/redemption to the same wallet, and funded Kalshi contracts on a dedicated subaccount. Its accounts, budgets, nonces and order IDs cannot share another ledger. This supersedes the observation-only restriction for these specific server adapters, not for research records, legacy spot, payments or model tools. Live remains disabled by default and needs separate local credentials, owner enablement, eligibility and completed Demo acceptance. Test operations are never revenue. See `docs/29-execution.md`.
- On 20.10.2026 the owner authorized moving the farm to a new Timeweb VPS and running all directions there, including `core/execution` in Paper/Demo; Live stays behind the existing acceptance gates and explicit owner enablement. See `docs/34-launch-timeweb.md` and `docs/35-owner-actions.md`.
- On 20.10.2026 the owner authorized computer use: GPT-6 Astra (paid OpenRouter route, shared budgets) drives a browser on a **separate VM** (`vm-agent/`) to search for legal earning opportunities and carry out tasks autonomously. Isolation is how it gets freedom: inside the VM browser it may browse the open web; it never gets exchange keys, wallets, the farm database, secrets or policy editing. Every action is validated with zod and `core/computer-use/policy.ts` before the VM is contacted; payments, credentials, registrations, publishing, messages, terms and transfers wait for owner approval in the office; verification bypass, multi-accounting and fraud are refused. Findings are records, never revenue. See `docs/32-computer-use.md`.
- On 20.10.2026 the owner decided how direct clients pay: freelance platforms pay through their own systems (the owner withdraws manually); foreign direct clients may pay USDT to the owner's Bybit deposit address (`PAYMENT_USDT_*`). Russian residents may not pay for services in crypto (259-FZ): the address is for foreign clients only and the UI and docs say so. The farm watches deposits with a separate **read-only** Bybit key (`BYBIT_WALLET_READ_*`, refused unless `readOnly=1`) and never gets transfer or withdrawal rights. Deposits are real income in their own coin, never converted to rubles, and count only after the owner marks them "income"; own transfers are marked "not income". See `docs/34-launch-timeweb.md`.
- On 20.10.2026 the owner decided that computer use earns on freelance platforms autonomously: the model assesses found jobs itself (`note_opportunity` with decision/fit), writes proposals in the first person on behalf of the account owner (a real person responsible for the work; AI is not mentioned), sends them itself on platforms where the owner logged the VM browser in, fulfils won text jobs and escalates to the owner only when it cannot proceed. Server-enforced limits: jobs whose text forbids AI/neural networks/ChatGPT are skipped; no invented credentials, degrees, reviews, portfolio items or years of experience; no off-platform payment or contact details; a direct client question about AI is never denied but escalated through `request_approval`; per-platform daily proposal limit (`COMPUTER_USE_PROPOSALS_PER_DAY`, default 15); sending needs the env gate `COMPUTER_USE_AUTO_PROPOSALS`, the office switch and a single-use 15-minute permit per send; no payments, withdrawals or credential entry by the model (the owner logs in through the remote-control panel). See `docs/32-computer-use.md`.
- On 27.10.2026 the owner decided that the model logs in to freelance platforms itself. The owner stores a platform login and password in the office; they are encrypted at rest (AES-256-GCM, key derived from `SESSION_SECRET`) and never reach the model, the step log or the audit. The model only calls `log_in` with a platform domain; server code checks the stored login, an https page of that platform (or of the owner's login page host) and a daily attempt limit, then the VM fills the fields and presses Enter. SMS/e-mail codes, captchas and login confirmations go to the owner. One stored login per platform; registration, multi-accounting and verification bypass stay forbidden. See `docs/32-computer-use.md`.
- Preserve archived strategies, product snapshots, obligations, audit records and idempotency keys.
- Never weaken tests, security or operating limits to make a demo pass.

## Verification and handover

- `npm run typecheck`, `npm test`, `npm run test:integration`, `npm run build` for meaningful application changes. Integration tests need a separate database ending in `_test`.
- `npm run format:check` for formatting. Check changed UI with Playwright.
- Keep `docs/STATUS.md` honest about real external integrations and uncompleted acceptance checks.
- Commit complete, verified work in small independent commits. English conventional commit messages, no model attribution or bot coauthors. Check commit author and message before finishing.
- Never commit `.env`, credentials, private keys, database dumps or customer material. Credentials are configured locally / on the server, not sent through chat.
